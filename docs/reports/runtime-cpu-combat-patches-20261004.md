## 清剿边界问题与实现

原生 tick74111268：E3N57 三塔能量9、3、1，均不足10点开火；红、绿各5000HP、无疲劳，在 E2N57(48,28)/(48,29)。tick74112042仍在原房(49,28)/(49,29)，TTL仅48。唯一敌人位于(18,27)，身体2WORK/2CARRY/4MOVE，载能20；最近塔(24,28)，其余两塔(14,6)/(13,8)。现役队在发布前已消耗绝大部分寿命，不把服务器通过当作已救回现役队。

旧逻辑见到库存或敌人便把所有塔都视为立即填满；按未来只剩尾部MOVE的退出速度逐格乘塔伤，并完全不计治疗，导致第一步被拒绝。v9 做如下改变：

1. 每次决策重新读取塔能、敌方 CARRY、库存和出生状态。当前不足10点的塔在搬运者物理最早送达前不计攻击；新CARRY+MOVE至少出生6tick，正在出生者用剩余出生时间。忽略取能、转移耗时，保守低估补能等待；有能量塔按持续可攻击计，不预支耗尽。
2. 两条实际BFS退路保存每塔沿路最大伤害。每座塔单tick最多集火一个成员，以两路较大值累计队伍总缺血。近身治疗较伤者至少能治疗总缺血的一半，抵扣量同时受当前活HEAL、强化和预测损毁下限约束。
3. 仅在同房、近身且两条退出路径逐格保持治疗距离时抵扣治疗。总缺血全部压到任一成员来计算最坏存活MOVE/HEAL，退出节奏收敛后才放行，至少保留1000HP。跨房余量不抵扣治疗；近身撤退一员疲劳时同步等待，避免治疗证明与实际执行分离。
4. 推进仍要求预计合并塔伤严格低于实际治疗；等于治疗不推进。塔补能、身体损毁、疲劳、搭档丢失、视野消失、墙造成的长绕路和不可达出口均重新校验。
5. 身体模型和标量预算只在单次决策内复用；没有长期生命值/塔能缓存，没有给小队增加通用让路豁免。

塔伤按原始伤害保守预算，尚不抵扣 TOUGH 减伤；这不会低估威胁，但可能限制强化队推进。NPC默认配置与历史16/18跳路线迁移仍属于未完成的架构候选任务。

身体回填、伤害与治疗结算的依据是 Screeps 官方 engine 的 `creeps/tick.js`、`_recalc-body.js`、`heal.js`，并以当前原生 room/creep 状态校验。
