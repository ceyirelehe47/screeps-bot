# CPU 与巡逻寻路修复验收记录

日期：2026-10-15。线上目标：账号 forster、Screeps.com、shard1、default 分支。部署版本 `2026.10.15-3`，生产源码提交 `a5aa8e772a83a47cc70ac2d4b05300e055c0ee34`。本记录后的文档提交不改变已部署源码。

## 为什么以前那么多测试没有发现问题

以前的测试证明了部分选择分支与当帧安全约束，却没有证明小队最终能走到目标。这是测试设计和验收的缺口，不能用通过数量掩盖。

| 旧测试的前提或断言 | 漏掉的实际行为 | 本次新增的验证 |
| --- | --- | --- |
| 手工预先设置攻击兵本 tick 的移动意图，然后只执行治疗兵 | 治疗兵先执行时没有看到新意图；攻击兵随后走了，治疗兵没有同步跟进 | 两种角色执行顺序、真实角色调用、帧末结算位置、连续多 tick 保持相邻 |
| PF mock 返回不连续且未抵达目标的路径，移动函数直接返回 OK | 调用成功但一直不移动，或者一直不能走完弯路，也能通过 | 从 terrain 与业务 callback 矩阵生成连续路径，执行真实共享移动栈，绕弯抵达 range 1，并检查墙血量不变 |
| 只断言障碍存在或目标失效当帧等待 | 永久等待也满足断言 | 实体阻挡两 tick 后移除，必须恢复推进并抵达目标 |
| 独立目标选择未覆盖共享巡逻的中性墙与清场最后敌兵 | 有路时仍把弱中性墙当任务目标；设施清完后忽略远处敌兵 | 中性墙不能抢占开放敌目标；真正必要破障保留；设施全清后继续追击合法敌兵 |

新增网格适配器是本仓库实现的 A* 与帧末结算，覆盖墙、占位、同格争用和阻挡传递。它不是官方引擎，没有完整覆盖跨房、身体与地形疲劳生成、塔伤和所有第三方意图裁决。线上连续帧用于补充验证实际行为。

## 先在旧代码上复现失败

有效红测试都因业务断言失败，运行错误为 0；编译失败和适配器缺少原生重载的早期轮次另存，未计为业务复现。

- 编队三 tick 结算：旧源码攻击兵先执行通过，治疗兵先执行失败；第一帧绿兵预期 x20、实际 x19。
- 真实移动栈四例：旧源码攻击兵先执行的绕弯、阻挡恢复通过；治疗兵先执行的两例因实际队形分离失败。相同测试文件在最终源码上全部通过。
- 共享巡逻目标：开放 rampart 被弱中性墙抢占、仅中性墙时仍错误产生目标，共两例失败；必要破障和开放设施的控制项保留。
- 清场远敌：worker、defender 两例预期选择敌兵，实际 null。
- CPU：低余量误准入、余量耗尽后继续扫描、一次准入重复读取危险信息，共三例失败。

对应测试：`src/roles/warDuoMovement.integration.test.ts`、`src/roles/healer.test.ts`、`src/roles/meleeAttacker.test.ts`、`src/runtime/powerBankHarvest.test.ts`。独立测试缺口审计与原始红测试位置见证据目录。

## 代码修复

攻击兵新提交有效移动意图后也协调治疗兵跟随；两种执行顺序共用幂等 helper。疲劳、已知占位或预约冲突、治疗兵原生移动失败时，只取消攻击兵自己本次新意图，保留治疗兵已有动作。编队等待返回 busy，不授予无路拆墙许可。出口协调和耗塔安全门保留。

共享巡逻从独立清场目标中排除中性墙；真正位于实际目标突破路径上的墙仍可攻击，普通清墙和其它任务身份保持原策略。没有任何设施或屏障目标后，再选择合法敌兵，危险敌兵优先，继续使用原有路径和耗塔安全门。

旧线上窗口 tick `74347374–74347444` 中，红兵停在 `(46,12)`，绿兵停在 `(45,12)`，记录了 68 帧攻击 `(47,11)` 的中性墙，同时存在通往敌 rampart 的开放几何路线。问题不只是“寻不到路”：中性墙本身被误当成了独立目标。开放几何路线不等于每一步双人战斗都安全，但足以反证该墙是全局物理必要破障。

## CPU 实际花费及修复边界

诊断版本 `cd3a1ac4` 的 7 个不同采样 tick 中，排除首次启动后的 6 个样本，PowerBank manager 平均 **47.5803 CPU**，路线状态及拓扑证明 `worldProof` 平均 **28.8392 CPU**，约占 manager 的 60.6%；Observer 平均 6.5957 CPU。7 个样本均没有新的原生 PathFinder 搜索。因此此前主要成本不能归因于“每几百 tick 的全图扫描”或新寻路。

巡查周期与 discovered 任务准入评估是不同循环。旧准入在 CPU 余量不足时仍重复扫描来源、资源和测距缓存证明；底层测量拒绝工作又不消耗次数配额，次数配额无法阻止这些前置成本。`worldProof` 还包含原生地图状态读取与拓扑校验，不能把全部耗时说成哈希计算。

修复复用现有 CPU 余量门，低余量延后新准入，继续观测、威胁、战斗、运输与生命周期；一次同步评估共享危险集合；Search、RouteCache、PathDistance 共享同一原生帧内的地图状态和出口事实。下一 tick、Game/map/reader 身份变化即失效。所有权、危险、拓扑和最终许可不做跨帧安全缓存。

部署后冻结了 18 个不同 tick 的详细快照。11 个低余量样本延后新测距；另 7 个样本恢复真实原生 PathFinder，manager 为 **7.5581–23.5969 CPU**，其中 `PathFinder.search` 调用（含 roomCallback）**5.3777–20.1557 CPU**、`worldProof` **0.1594–0.2700 CPU**。新测距确实恢复，任务测量时间也继续更新；不能把低余量跳过业务时的低耗时当成同负载优化收益，也不能据此称已接纳或生成新 PowerBank 队伍。
