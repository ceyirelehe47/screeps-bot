# Memory 许可链堆缓存与分段迁移

实施开始于 2026-10-16，最终验证延续至 2026-10-17（Asia/Shanghai）。延续第一批 CPU 优化 `90b4ef18`，在 `codex/memory-permit-cache-20261016` 实施。第一批结果见[CPU 优化验证](./2026-10-16-cpu-optimization.md)。

## 实施范围

已实现 V3 `Memory.data.marketSaleAutomation.directAutomation.baseResourceV3.permitChain` 的压缩分段、双 bank 回读切换、解码结果堆缓存及失败关闭门禁。默认关闭，没有改动游戏中的 Memory 或上传代码。

业务层每 tick 仍拿到完整许可链，执行原有的授权、activation anchor、WAL、余额责任及当前事实校验。存储 manifest 的摘要只检查存储一致性，不能授权交易。现有许可摘要、permit epoch 和账本格式保持原样；存储代次使用单独的 `epoch`。

### 持久化与恢复

1. 显式配置两组互不重叠的 segment ID；每组 1–4 个，ID 为 0–99，排除当前遥测 ID（默认 90）。激活请求经已有协调器合并，最多申请 active 加待写 bank，并保留其它调用方的申请。
2. 写入前确认空闲 bank 已在当前 tick 加载，且内容为空或属于本存储命名空间。保护当前 active bank，拒绝覆盖其它用途的数据。
3. zlib 压缩、base64 编码后分为最多 4 片，每片数据最多 90,000 字符，连同 envelope 低于每 segment 100 KB 上限。原始 UTF-8 JSON 最多 1,500,000 字节，容量不足保留完整链。
4. 写入 pending 代次时主 Memory 保持完整链。只有下一 tick 真实回读全部片、核对代次、顺序、长度、payload 摘要、zlib 校验和及完整 JSON 摘要通过，且当前链的完整 JSON 仍相等，才提交 active 元数据。
5. 驱动落盘时返回派生的 Memory 根，将完整链替换为小型 manifest。运行时 Memory 保持完整；提前查看内部 `_parsed` 仅生成投影，不触发保存。console 后续修改和显式 `RawMemory.set()` 仍有最终效力。
6. 新许可或 console 改变当前链时，保存最新完整链并进入 inline 模式，之后再写另一 bank。落盘前再核对当前 segment 字符串，避免其它调用方同 tick 覆写片后留下不可恢复的引用。旧 bank 保留。
7. 关闭功能时先展开完整链，再保存 inline；确认回到 inline 后，后续 tick 不再申请旧 bank。若片未加载、损坏或冷解码预算不足，则保留引用与元数据并等待；不会把历史静默重置为空。

主循环只增加阶段前展开和收尾持久化接入，已有生产阶段顺序保持原样。启动时发生的解析/展开及引擎最后序列化不属于市场 phase；不能只依据某个 phase 的下降推断总 CPU。

### 堆缓存

最多缓存两个 manifest 的解码结果，key 包含 shard 与 manifest 摘要。每 tick 仍将当前实际加载的每片字符串与缓存原文逐一比较；变化后必须重新校验和解码。不会用旧堆对象掩盖外部坏片。

解码结果是从 JSON 重新构造并深冻结的普通数据。相同对象可跳过重复 JSON 编码；新对象仍比较完整 JSON。缓存不保存“已授权”结论，同 tick/跨 tick 的业务恢复与写前门禁继续执行。

冷解码和新分段准备默认要求 bucket 至少 9,000，剩余 tick CPU 至少 150；`minBucket` 可在 0–10,000 配置，`minFreeCpu` 最低 50。热命中不需要再次解压。冷启动因 segments 次 tick 生效，可能先等待一 tick；等待期间市场、Terminal 主动动作和受市场库存保护的出库均保守拒绝，其它生产阶段继续执行。

### 整棵 Memory 缓存的取舍

测试了两种保留原生 JSON 值语义的整棵缓存：独立归一化和结合 stringify 的归一化。与原生 parse/stringify 的输出一致，也能涵盖 console 写入和失败 tick，但真实快照的完整生命周期对照分别变慢约 41.23% 和 59.08%。因此未接入，也未保留可启用的生产开关。试验源码、失败收益测量及日志仅保存在忽略目录。

本次 Memory 堆缓存的落地点是冷许可链。整棵 Memory 的复用仍待更低成本的正确实现，不能把本次工作描述为已经跳过全部 `JSON.parse(Memory)`。

## 验证与测量

所有类型检查、测试、压缩与性能测量、构建都在服务器任务隔离目录执行；本机仅编辑、查询及传输。没有传输部署凭据。

真实数据采用服务器原有的 2026-10-10 历史快照。比较基线为已包含第一批优化的代码；每组交替先后顺序，7 组、每版每组 12 帧。计时包括主 Memory 解析、许可展开、完整市场预检、console 写入和驱动实际保存。首次迁移的 3 帧准备和结果摘要不计入 warm 计时。

## 启用与回退约束

配置入口为 `Memory.cfg.memoryStorage.permitChain`，字段包括 `enabled`、`banks`、`minBucket`、`minFreeCpu`。未选择线上空闲 ID，因此没有提供可直接执行的启用命令，也未自动迁移真实数据。

上线时需要先核对目标运行时的 `_parsed` 兼容性和 segment 使用情况。该私有接口仅用于给驱动提供保存投影；缺少可配置数据属性时不准备分段，已展开的链回退完整存储。兼容性依据当前公开的[engine Memory getter](https://github.com/screeps/engine/blob/master/src/game/game.js)和[driver 保存流程](https://github.com/screeps/driver/blob/master/lib/runtime/runtime.js)核查；实际线上运行时尚未验证。异步激活、100 KB 分段及最多 10 个激活片的限制依据[官方 RawMemory API](https://docs.screeps.com/api/#RawMemory)。

回退旧版代码之前，须先在当前代码关闭功能，等待片加载并确认**实际保存**的主 Memory 已为 inline 且包含完整链，再切换旧版。缺片时保留当前代码和引用恢复，不能通过删除元数据来“解除”门禁。旧 bank 不自动清理。本轮未执行上线、启用或回退。
