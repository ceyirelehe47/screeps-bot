# 战争调度优化方案

- 仓库：`ceyirelehe47/screeps-bot`，基线 `origin/main` `a9c1f81`（2026-10-16 21:19 +0800）
- 范围：`src/runtime/warControl.ts`（2112 行）及战争角色 `meleeAttacker.ts`（991）、`healer.ts`（286）、`towerDrainPair.ts`（777）
- 说明：本文只依据源码静态分析和仓库内已有报告。仓库里唯一可引用的 War 实测是 `docs/reports/runtime-observation-combat-cpu-20261004.md`：War 调度阶段均值 1.33 → 1.26 CPU（v13→v14，68–71 creep）。那之后的版本没有单独实测，文中不编造新数字，只给复杂度和调用次数。

---

## 1. 结论

“笨重”主要来自两层，第二层更贵：

1. **调度层（warControl）**：采用“每 tick 全量重建”。任务身份靠 configName 字符串前缀表示，所以每 tick 都要反复扫描 `Game.creeps`、`Memory.creeps`、所有房间的所有 spawn 和 config store 才能知道“我有谁”。排队任务和共享小队的非 owner 任务每 tick 还会重复执行“撤销/回收”这类副作用，即使状态完全没变。单任务成本不高（2026-10-04 约 1.3 CPU），但它随 **任务数 × creep 总数 × spawn 数** 线性放大，而且每 tick 都会把 Memory 写脏。
2. **角色层（creepWork 内）**：攻击兵在目标房里每 tick 都会重新构造 CostMatrix，并对多个候选目标做 PathFinder（单次上限 2000 ops，open/breach 各一次），移动又用 `reusePath: 0`。耗塔双人组每 tick 构造多个 2500 格数组并做 BFS。这部分成本算在 `creepWork` 里，不计入 War 阶段，所以 War 阶段看着只有约 1.3 CPU，实际总开销被低估了。

建议顺序：**先补埋点（P0），再按 P1 → P2 → P3 做**。P1 是不改行为的去重/幂等化，风险最低；P2 处理角色层寻路缓存，收益最大，但需要守住安全语义；P3 是架构拆分。

## 2. 现状画像

### 2.1 运行路径（每 tick，`runWarControl`）

```
runWarControl
├─ 所有 terminal 任务：assetsReleasedAt 检查
├─ runSharedWarSquads          ← 共享小队组（每组每任务）
├─ 按 sourceRoom 分组
│   ├─ 串行候选：非 active 的 → parkQueuedFrontline（每 tick！）
│   ├─ active → activateFrontline + processTask
│   └─ towerDrainDuo 全部并行 → processTask
├─ 所有任务 updatedAt = Game.time  （每 tick 写 Memory）
├─ runWarRebuildWatches
├─ runNpcLootHandoffs          ← 再算一次 getHostilePresence
└─ writeWarTelemetry           ← 所有任务（含 done/failed）再算一次 hostile + 扫 Game.creeps
```

### 2.2 复杂度来源

- 3 种 squad（standard / t3Duo / towerDrainDuo）× 4 种运行模式（串行、耗塔并行、共享小队、巡逻），另有重建监视叠加在上面。`isTowerDrainDuoTask` 在文件中出现 21 次，`isT3DuoTask/isDuoTask` 出现 19 次，分支散落在各个函数里。
- `WarTask` 约 40 个字段，状态机没有显式的转移表，`status` 由多个函数各自 `setTaskStatus`。
- 同一个文件里同时承担了状态机、spawn 队列管理、强化准备、共享小队、巡逻、重建监视和遥测。

## 3. 调度层热点（warControl.ts）

用 T 表示活跃任务数，C 表示 `Game.creeps` 数，M 表示 `Memory.creeps` 数，S 表示全帝国 spawn 数，R 表示自有房间数。

| # | 位置 | 每 tick 做了什么 | 代价 | 建议 |
|---|---|---|---|---|
| H1 | `parkQueuedFrontline` 1496 | 每个**排队中的**串行任务每 tick：`disableTaskProduction` → `getTaskConfigNames`（全量扫 `Memory.creeps` + config store 前缀列表）+ 每个 config 改写 spawnList + `setTaskCreepsQueued`（全量扫 `Game.creeps`）+ `releaseBoostLabs` | O(T_queued × (M + C + S)) | 只在**进入 queued 的那一帧**执行一次；之后靠 `status==="queued" && failReason==="frontline_queued"` 直接跳过。`_warQueued` 改在 creep 出生或配置时写一次 |
| H2 | `runSharedWarSquads` 1872 | 每个受管任务每 tick 调 `retireSharedController`（扫 spawning、清 config、改写 spawnList）；每个**非 owner** 任务每 tick 调 `retireSharedCombat`（`getTaskConfigNames` + 扫 `Game.creeps` + `detachWarTaskCreeps` 扫 `Game.creeps` 和 `Memory.creeps` 各一遍 + 所有房间 spawnList filter + 释放 lab） | O(T_shared × (2C + 2M + R·S)) | 加一个“已撤销”标记（例如 `task.sharedRetiredAt` 或依据 `!activeGeneration && 无配置`），已撤销的任务直接跳过；controller 撤销同理，只在发现有 claimer config 或 live actor 时执行 |

| H7 | `getHostilePresence` 698 | 同一任务同一 tick 最多算 3–4 次（processTask、runNpcLootHandoffs、telemetry、共享小队）；towerDrain 还会额外 `FIND_STRUCTURES` 筛墙 | 重复 find + filter | 用 `(Game.time, roomName, task 的 ignoreIds 版本)` 做 tick 内 memo |
| H8 | `writeWarTelemetry` 1328 | 每 tick 为**所有任务（含 done/failed）**构建快照；`getTaskCreeps` 对每个任务全量扫 `Game.creeps` | O(T_all × C) | 改为每 10–20 tick 或状态变化时写一次；terminal 任务冻结最后一份快照；creep 列表走 config 索引 |
| H9 | `runWarControl` 末尾 | 所有任务每 tick 都写 `updatedAt = Game.time` | 每 tick 写 Memory | 只在真正发生变化时更新，或干脆删除（statusSince 已经够用） |

## 5. 架构调整（P3，做完 P1/P2 后再做）

### 5.1 拆分文件

```
src/runtime/war/
  store.ts           WarTask 类型、迁移、读写
  fsm.ts             显式状态转移表 + onEnter/onExit 副作用
  admission.ts       每个 sourceRoom 决定谁是 active（合并 串行 / 耗塔并行 / 共享 三条路径）
  production.ts      config 生成、spawn 入队、强化门（幂等、版本化）
  squadPolicy/
    standard.ts  t3Duo.ts  towerDrainDuo.ts   各自实现 bodies()/boosts()/parallel()/clearCriteria()
  shared.ts          共享小队 owner 选择与成员转移
  patrol.ts          巡逻推进
  rebuildWatch.ts    重建监视
  telemetry.ts       低频遥测
  index.ts           runWarControl 编排
```

### 5.2 三个关键改法

1. **显式成员表代替前缀反查**：`task.members = { [role]: { configName, creepName?, spawnedAt? } }`，生成、出生、死亡、转移时维护。`getTaskConfigNames`、`detachWarTaskCreeps` 和 telemetry 都改成 O(成员数)。
2. **状态机副作用只在转移时执行**：`queued` 的 onEnter 停止生产、释放 lab；`deployed` 的 onEnter 释放 lab、清 config；terminal 的 onEnter 回收资产。稳态 tick 只做观察和判断，不写 Memory。H1、H2、H3 会自然消失。
3. **SquadPolicy 接口**：把 21 处 `isTowerDrainDuoTask` 收敛成 `policy.parallel`、`policy.needsBoost`、`policy.countsNeutralWalls`、`policy.allowsControllerAttack` 等字段，以后加新阵型不必再改十几个函数。

### 5.3 节奏分级

- `staging` 且无视野、`patrol_waiting` 未到时间、`queued`：设置 `nextCheckAt`，每 5–10 tick 才跑一次调度（creep 自身每 tick 照常行动）。
- bucket 低于阈值时，遥测和重建监视的观察请求降频，战斗中的任务不降频。

### 验收口径（沿用仓库已有做法）

- 同输入 A/B：固定 creep 数和任务数，统计每 tick `Game.creeps` 和 `Memory.creeps` 全量扫描次数、PathFinder 调用次数和 CostMatrix 创建次数。2026-10-04 那轮用的就是这种口径，例如“creep 集合扫描 4750 → 250”。
- 实服：只比较同负载窗口内的 `warControl` 阶段和 `meleeAttacker/healer` 的 role CPU。不要把整体均值变化归因于本次修改。
