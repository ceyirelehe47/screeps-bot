## 2. 上轮失败：已观察事实与尚未证明的解释

上一轮原始材料支持：

- 正式配置 T=332，预期窗口330–352。
- `run-treasury` 于 `2026-09-10T04:16:37Z` 左右恢复；目标用户没有实验样本，工具以 `user_console_stalled` 判停。

- runner/processor 的进程出生时间，比 launcher/main 晚约1小时。Agent 将故障归于 `restart_interval=3600` 的滚动重启与主循环恢复。

本轮应采用的结论是：

**没有取得本地国库闭环实证；暂停标志与短暂 tick 不变没有排除当时尚未完成的处理。**

不要照抄“不是任何被测代码缺陷”“没有Windows错误事件便排除了OOM”“重启后报价和实扣必然一致”等过强解释。计划重启是有证据支持的排查方向，完整因果必须依据实际安装代码、启动参数及时间线；本轮没有发送之前，也不能宣称已经验证实扣。

## 6. S02：环境就绪、控制往返与真正完成的tick

### 6.2 一次完成地图与fixture，再统一启动一致的进程

业务范围固定为同一新建合成用户：

- 源 `W1N57`，目标 `W10N57`，两端可用Terminal，资源H，单笔100。

- 其他默认NPC若存在，明确记录并确认不参与两个实验端点，不能声称整个世界绝对无其他bot。

先完成地图、地形、归属、结构、库存及必要缓存更新，记录最后管理修改的真实ISO时间。之后**统一停止并重新启动本次实验引擎相关进程**，不是只重启runner。原环境有无在途工作须在清理前记录，不能拿本次准备去恢复旧失败实验。

必要的存储保存、正常关闭和重启后读回要有原件；整树重启后重新确认世界/对象没有丢失。不要把强杀前的内存快照当作磁盘已经持久化的证明。

### 6.3 建立准备期完成屏障，不只“多等几秒”

**本节是准备与正式装载前的额外环境准入检查，不是宣称现有 `runSession` 已具备新原子暂停能力。**

在无send入口下，保存一段连续的真实目标用户样本和引擎处理事件。至少能够观察到多个完整的用户/房间处理周期；周期应适配当前工具约1秒/tick、连续5秒无目标用户console就判停的条件。不能用外部ping、其他用户console或管理数据库读回冒充目标用户运行。

每次准备期暂停后，尤其是初始化控制槽前、arm前、observe-armed结束及最终装载前，应联合确认：

1. 与本次准备恢复关联的最后一个已启动tick，其用户处理和房间处理已完成。使用已核实含义的真实引擎完成事件或状态，例如相应的 `roomsDone`，并保留原始封装。
2. 完成事件之后的Game.time、暂停标志和对象/控制读数相符；不存在已观察到的下一轮启动而未完成的处理。
3. 没有尚未完成的 `Main loop reset`、滚动重启或worker更替。发现更替时，本次旧就绪证据不继续有效。

`tickStarted.payload="1"` 不是实际游戏tick；原始事件中“刚处理完的tick”和“下一tick编号”的关系，按实际安装源码与采样对应核对，不猜测加减1。不能仅凭`paused=true`、一次稳定计时或`system.pauseSimulation()`返回OK就宣布已经排空。

辅助采集只读，不修改队列/数据库来伪造“已完成”。取不到可信完成依据、环境持续恢复、或出现暂停后迟到推进时，**不arm、不固定最终T、不装载启用的正式bundle**，保存缺口并结束受影响的步骤。若这暴露工具功能缺失，按第3节交回修补，不自己添加新屏障协议。

### 6.4 真实Memory往返

## 9. S05：独立验收、停止与判定

### 9.1 三个问题必须先答

1. 是否真正到达一次 `terminal.send()` 调用边界？确切T、完整参数和同步结果是什么？
2. 是否观察到100H从源到目标，且这一次经过国库接纳、占用与注册结算？
3. 是否及时停止，未决事实是否保留，绑定进程是否由工具自动确认退出？

“没有看到交易”不能单独回答第一个问题；“返回OK”不能单独回答第二个；“后来手工发现进程已死”不能冒充第三个中的自动确认。

### 9.2 国库与真实世界联合核对

使用原始目标用户console、前后Memory/对象/交易快照，检查下列闭环，不只信 `treasury-verification.json` 的最终标签：

| 时刻/阶段 | 必须看到的事实 |
| --- | --- |
| 正式前 | 新世界没有旧treasuryCore业务；本轮控制槽armed=true、attempted=false；两端与真实基线一致 |
| T的观察前态 | observer先采样，世界尚未包含此次send效果 |
| 接纳 | 本轮workKey/attemptId的pending；源H100、energy q及目标容量100被实际查询口径占用 |
| dispatch后 | 恰一次边界；OK时仍为`outcome_unknown`，不以接口接受立即释放风险 |
| 后续观察 | 完整description、两方身份、路线、H100、唯一T、唯一交易ID，出向/入向/数据库记录相符 |
| 注册结算 | 通过现有注册reconciler，不是管理员自报receipt；核对世界变化与Treasury observation |
| 覆盖与退出 | closing期间可见的查询不双扣；终态active真正退出、资源/费用committed=0、源spendable回到实际库存、目标风险调整空位等于实际空位 |
| 单次边界 | 控制attempted@T保留；admitted/dispatched/settledCommitted各1，rearmings=0；没有其他send入口或第二笔 |

查询必须使用现有 `service.query` 的实际占用语义与 `riskAdjustedFreeCapacity`，不得将subtractOutgoing/subtractReservations关掉来显示“余额正确”。对当前日志中存在的`reconciled`/closing中间态逐项读取；缺失就报告证据缺口，不临时制造快照或把离线样例冒充实机。

### 9.3 费用与容量

分别报告冻结报价q、费用上限cap、实测源energy净减少量。无其他相关writer的本场景中，沿当前实现接受 `1 ≤ observedFee ≤ q`；低于q时保留差异说明，不改q、不补扣或把差异自动归为已证实的引擎特性。

不能因为这次统一启动了进程，就提前宣称“报价与实扣同源且一定相等”。

### 9.4 停止和撤装的四层事实

依次区分：

1. 何时收到窗口完成/故障信号，何时实际发出暂停请求；完整窗口情况下延迟须满足现有限值。
2. 暂停响应、标志、tick，以及最后在途tick的真实完成；自然完成当前tick使最终编号前进，不自动等于额外一次发送。
3. 撤装写入及读回，attempted/同步结果未丢失；存储读回不宣称已完成driver或磁盘持久化。
4. `process-stop-result.json` 的实际绑定身份、退出对象、耗时、审计错误，以及最后一次独立进程/监听核对。

原`runSession`的错误路径仍按现有代码执行，本任务**没有修复其暂停原子性**。若再出现 `world advanced after write`，保留整个时间线并如实判失败/未确认；不能用手动覆盖Memory、重启同一世界或第二次撤装去伪装首次成功。

发生收尾异常时，不恢复世界；允许在已记录所有权范围内补充只读诊断和终止本次进程，日志中区分工具第一次结果与后续应急清理。不清理不属于本次的旧收集器。环境目录在证据归档、必要原始存储留存和进程退出确认前不得删除。

### 9.5 结果标签不合并

- **PREP_BLOCKED / LIVE_NOT_RUN**：没有进入正式恢复，说明具体阻断及是否涉及工具修补。
- **LIVE_FAIL / INCONCLUSIVE**：正式运行出现故障、缺证据或未闭环；保留工具原始状态，不改为PASS。
